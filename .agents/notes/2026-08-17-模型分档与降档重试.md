# 模型分档：简单消息低推理 + 任务档失败降级重试

## Problem
微信桥所有消息固定 `flash + medium`（老板指定），问候/确认类简单消息也花同样的推理成本；复杂任务用 task 档失败后直接回"任务执行失败"，没有重试路径。对比 OpenSquilla 的智能路由（LightGBM 分类 + C0-C3 四档 + fallback 链），我们不需要上 ML 分类器和多档模型——单机桥 + 固定模型分工下是过度设计。

## Decision
只借鉴两个低成本点：
1. **casual 档降推理**：`classify_message` 已有的 casual 等级（问候/确认）改用低推理档（`casual_effort`，默认 `low`），普通对话仍 `chat_effort`（medium），复杂任务仍 `task_effort`（medium）。`backend.json` 可覆盖，默认不改变老板指定的分工。
2. **task 档失败降级 chat 档重试一次**：复杂任务 task 档（模型/effort 与 chat 档不同时）失败且未被打断、未 /stop 时，自动用 chat 档重试一次，提高任务不失败概率。

## Alternatives considered
- 整套移植 OpenSquilla 的 RoutingPolicyEngine / LightGBM+ONNX 分类器：依赖重、单机微信桥收益低，"省 60-80% token"无基准支撑，不采用。
- 降级重试无限次：可能反复失败拖死任务线程，只重试一次。
- 被打断/停止后仍降级重试：会覆盖用户意图，跳过。

## Consequences
简单消息（问候/确认）推理成本降低，任务失败多一次兜底。代价：casual 档回复可能略"浅"（低推理），但只影响问候/确认类；降档重试会让失败任务多花一轮时间（已限制一次）。
