# 审核修复批次（2026-08-15）：fail-closed、HANG 守卫、work_dir 兜底、限流锁外、打断仅 codex

## Problem
外部审核发现 6 项问题：①全新 clone 无 backend.json 时 work_dir 落到启动目录（注释承诺“仓库根 wechat_work/”未兑现，非崩溃但文件跑错地方）；②仓库版 HANG 每次重启连接，与决策笔记“第 3 次才重启”矛盾；③发送方校验 user_id 为空时 fail-open（+danger-full-access = 任意 RCE 风险）；④运行版与仓库版 helper 对“▶️ 正在执行命令/工具”模板分叉；⑤打断恢复只对 codex 有效但文档未说明；⑥`_throttle_send` 持锁 sleep 会卡住所有发送线程。

## Decision
- work_dir 未配置 → `HERE.parent / "wechat_work"`（仓库根）。
- HANG：`attempt >= 2` 才 `_helper_restart()`，前两次只中断重试（与决策笔记、运行版一致）。
- 发送方校验 fail-closed：`from_user != user_id` 一律拒收；user_id 缺失启动时告警提示重绑。
- `_throttle_send`：sleep 移到锁外。
- 打断恢复仅 codex：`_preempt_task` 对非 codex 直接 return（避免 claude/generic 完成后被误判打断、结果丢弃重跑）。
- helper 统一为运行版行为：工具事件只发 activity 心跳，不再发“▶️ 正在执行命令/工具”机械模板（25s 保活提示已覆盖 liveness）。

## Alternatives considered
- user_id 缺失时拒绝启动：会卡住合法注册流程，改为“启动告警 + 运行时拒收”。
- 保留机械模板：简单消息被骚扰，已实测弃用。
- claude/generic 也实现打断：需进程级 interrupt/resume，超出本次范围，文档注明限制。

## Consequences
开源版与运行版行为一致、开箱即用、安全默认闭合。代价：claude/generic 后端任务不被聊天打断（后台跑完）；无 user_id 的异常账号完全不可用（需重绑，属预期安全行为）。
